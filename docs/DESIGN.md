# 产品与系统决策

家人在沙发上需要做的事是找到歌、知道何时轮到自己、听到伴奏。曲库整理、文件格式和下载错误留在管理员页面。首版用一个客厅，把这些动作做成明确的闭环。

| 用户动作 | 系统行为 |
| --- | --- |
| 点已有双版本歌曲 | 立即加入队列，默认伴奏 |
| 点未准备的本地歌曲 | 创建 NAS 预处理任务，完成后入队 |
| 本地没有歌曲 | 展示在线伴奏搜索结果，由用户选版本 |
| 在线资源选定 | 下载、预转码、按配置预分离，完成后入库入队 |
| 视频不可得但音频可得 | 音频配背景和歌词临时播放，标记待补视频 |
| 家人同时操作 | NAS 统一裁决，去重，旧切歌请求返回冲突 |
| NAS 重启 | 数据库保留队列，未完成任务重新处理 |

NAS 服务由 Express、SQLite、单个后台任务执行器组成。浏览器使用 React，通过 REST 提交操作、SSE 接收队列和互动事件。媒体经过 FFmpeg 归一到 H.264/AAC MP4，按字节范围传给电视。避免依赖不同电视浏览器的音轨切换 API，原唱和伴奏各自保存一个播放文件。

电视 APK 使用原生 Activity 设置连接地址、保持横屏与常亮、支持全屏媒体；WebView 展示 NAS 提供的界面。电视只解码和呈现，界面更新随 NAS 服务更新。手机使用独立响应式入口，不启动视频播放器。

AI 分离是可选任务阶段。优先使用已有伴奏，其次使用正确配置的音轨/声道。启用分离后才处理原始混音，结果留在 NAS。AI 服务可位于第三方，也可以是单独的 Demucs 容器。视频搜索结果中的“伴奏”只是检索线索，不能可靠证明没有人声，所以提供用户确认选项。

界面参考 [Emil Kowalski 的设计规范](https://github.com/emilkowalski/skills)，使用浅色背景、清楚的分区和紫色重点。高频方向键切换不做动画；鼠标或触摸按压提供轻微反馈；动效只用于鼓掌等互动，并尊重减少动态效果设置。电视字号与焦点独立加大，手机底部保留点歌与播放入口。

首版取舍：单客厅、单活跃电视、最多 100 首就绪队列，曲库每次搜索最多返回 300 条。没有多房间、演唱打分、录音、音高调节、会员资源、云账号登录或自动识别伴奏质量。曲库特别大时应进一步加入分页、索引与批量任务控制。播放器刷新后没有跨设备精确播放时间同步。

研究参考包括 [TuneScout-v2](https://github.com/yuwancumian2009/TuneScout-v2)、[用户提供的家庭 NAS KTV 文章](https://post.smzdm.com/p/a958pxd0/)和 [yt-dlp](https://github.com/yt-dlp/yt-dlp)。TuneScout 的当前公开目录主要是说明和图片，虽然 README 声称 MIT，未作为完整源码依赖。项目没有拉取或复用参考项目的容器实现。
